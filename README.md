# RAG-manual-searcher

Сервис для поиска ответов в учебных пособиях и вузовских конспектах по математике.
Пользователь задаёт вопрос на русском языке, а сервис ищет подходящие фрагменты
материалов и передаёт их языковой модели как контекст для ответа — подход RAG
(Retrieval-Augmented Generation).

## Возможности

- Регистрация, вход, выход и обновление сессии.
- Вопросы по учебным материалам с ответами языковой модели.
- Создание чата при первом вопросе, получение списка чатов и истории, удаление чата.
- Просмотр названий книг, используемых для контекста.
- Управление ролями и блокировками пользователей администратором.

Сценарии использования, ограничения и направления развития описаны
в [продуктовой документации](spec/docs/product.md).

## Стек и структура

Backend: Python 3.12+, FastAPI, Pydantic, SQLAlchemy и Alembic.
Хранение данных: PostgreSQL с расширением pgvector и Redis.
Поиск выполняет собственная реализация BM25 с разреженными весами в pgvector.
Чат использует внешний LLM API с fallback моделей; бенчмарк — Qwen 2.5 3B через Ollama.
Окружение: uv, Docker Compose, Prometheus и Grafana.

| Путь | Содержимое |
| --- | --- |
| `back/src/` | API, доменные модели, поиск и работа с хранилищами |

| `back/scripts/` | Подготовка и импорт учебных материалов |

| `data/` | PDF, текстовые материалы и промежуточные данные |
| `infrastructure/back/` | Docker Compose и настройки мониторинга |

## Подготовка окружения разработки

Нужны Python 3.12+, uv, Docker с Compose и make.
Команды ниже выполняются из корня репозитория, затем из `back/`, как указано в примере.
При незавершённом слиянии сначала необходимо разрешить конфликты в коде.

```bash
cp .env.example .env
cd back
uv sync --dev
```

Заполните `.env` в корне репозитория:

- `LLM_URL` — адрес API chat completions, `LLM_API_KEY` — ключ провайдера.
  Модели чата и fallback задаются в `back/src/api/chat.py`.
  `LLM_MODEL` задаёт модель автономного RAG и бенчмарка.
- `JWT_SECRET` — собственный секрет подписи токенов.
- `APP_PASSWORD_SALT` — корректная bcrypt-соль. Сгенерировать её из `back/`:
  `uv run python -c 'import bcrypt; print(bcrypt.gensalt().decode())'`.
- `POSTGRES_*` и `REDIS_*` — параметры подключения. При локальном запуске приложения
  порты подключения должны совпадать с опубликованными портами `*_OUTPUT_PORT`.
- `BOOKS_DIR` — путь к PDF. Для запуска скриптов из `back/` используйте
  `../data/student_book_pdf` вместо пути из примера окружения.

Далее поднимите PostgreSQL и Redis и примените миграции:

```bash
cd ..
make back-dev-up
cd back
uv run alembic -c migrations/postgresql/alembic.ini upgrade head
```

Для импорта и поиска нужны русские ресурсы NLTK. Импорт из `back/`
сохраняет исходный текст страниц, нормализованный текст и индекс BM25:

```bash
uv run python -m nltk.downloader stopwords punkt punkt_tab
uv run -m scripts.data.data_migration --books-dir ../data/student_book_pdf
```

Повторный импорт восстанавливает исходные тексты существующих страниц
при однозначном совпадении названия книги и нормализованного текста. Проверьте
отчёт импорта по пропущенным страницам. Для перестроения индекса из уже
сохранённых чанков используйте `uv run -m scripts.data.data_migration --reindex`.

BM25 использует частоты термов, длины чанков, `k₁ = 1,2` и `b = 0,75`.
Нормализация запроса и страниц включает русскую токенизацию NLTK, удаление
стоп-слов и лемматизацию pymorphy3. Это позволяет находить разные формы
одного слова. Модель получает исходный текст с формулами и условиями.
Индекс строится при импорте. PostgreSQL суммирует веса терминов запроса
и отдаёт до трёх фрагментов.

Убедитесь, что Ollama запущена и модель установлена:

```bash
ollama pull qwen2.5:3b
ollama list
```

Запуск backend из `back/`:

```bash
uv run -m src.app.main
```

При стандартных `APP_HOST=localhost` и `APP_PORT=8080`:

- Swagger UI: <http://localhost:8080/docs>.
- Актуальная OpenAPI-схема запущенного приложения: <http://localhost:8080/openapi.json>.
- Проверка доступности PostgreSQL и Redis: <http://localhost:8080/health>.

Остановка окружения из корня репозитория: `make back-dev-down`.
Подробности окружения и команды Makefile — в [руководстве разработчика](spec/dev/manual.md).

## Бенчмарк НИРС

Набор содержит 30 фрагментов из математических книг, 10 обычных вопросов
и 5 ловушек. У каждого фрагмента указаны PDF и номер страницы, считая от
начала файла. Формулы приведены к текстовой записи. Разметка с эталонами
хранится в [data/benchmark/math.json](data/benchmark/math.json).

### Как запустить

Понадобятся Python 3.12+, uv, Docker Compose и Ollama. В корне репозитория
создайте `.env` из `.env.example`, если своего файла ещё нет. В Bash это
`cp .env.example .env`, в PowerShell — `Copy-Item .env.example .env`.
Для бенчмарка задайте `LLM_URL=http://127.0.0.1:11434/v1/chat/completions`,
`LLM_MODEL=qwen2.5:3b`, `LLM_API_KEY=ollama` и `LLM_REQUEST_TIMEOUT=120`.
Проверьте, что `POSTGRES_PORT` совпадает с `POSTGRES_OUTPUT_PORT`.

Из корня репозитория запустите PostgreSQL. Если Ollama ещё не работает,
откройте приложение Ollama или выполните `ollama serve` в отдельном терминале.

```bash
docker compose --env-file .env -f infrastructure/back/docker-compose.dev.yml up -d --wait database
ollama pull qwen2.5:3b
cd back
uv sync --locked --no-install-project
uv run --no-sync alembic -c migrations/postgresql/alembic.ini upgrade head
uv run --no-sync python -m nltk.downloader stopwords punkt punkt_tab
uv run --no-sync -m scripts.benchmark_rag --output benchmark-result.json
```

Если Ollama запущен в Windows, команды `uv` можно выполнить из PowerShell,
чтобы адрес `127.0.0.1:11434` указывал на Windows. JSON-отчёт появится в
`back/benchmark-result.json`. Для своего набора укажите `--dataset путь/к/набору.json`,
сохранив структуру разметки и объём контрольного набора.

CLI создаёт временные таблицы на отдельном соединении с PostgreSQL. Для
бенчмарка достаточно миграций, разрешения создавать временные таблицы
и установленного pgvector с поддержкой `sparsevec`. Импорт книг, запуск
backend и Redis для бенчмарка не требуются.
Отчёт сохраняет Recall@3, MRR@3, Accuracy, Correct Rejection Rate, число
отказов, ответы и причины вердиктов. Recall@3 и MRR@3 считаются по десяти
обычным вопросам. На них же Accuracy измеряет полноту и корректность
ответа по смыслу. Correct Rejection Rate показывает долю точных отказов
на пяти ловушках. В роли судьи выступает та же модель Qwen, поэтому
Accuracy отражает её автоматическую оценку. При ошибке генерации или
оценки CLI сохраняет неполный отчёт и завершает работу с кодом 1.

### Результаты контрольных прогонов

Два прогона Qwen 2.5 3B от 18 ноября 2026 на одном наборе вопросов.
[Первый отчёт](data/benchmark/qwen2.5-3b-results.json) ·
[Повторный отчёт](data/benchmark/qwen2.5-3b-repeat-results.json)

| Метрика | Первый прогон | Повторный прогон |
| --- | ---: | ---: |
| Recall@3 | 86,7% | 86,7% |
| MRR@3 | 1,00 | 1,00 |
| Accuracy по оценке Qwen | 20% (2 из 10) | 0% (0 из 10) |
| Correct Rejection Rate | 80% (4 из 5) | 80% (4 из 5) |

- BM25 поставил релевантный фрагмент первым для всех обычных вопросов.
  Например, в Q09 поиск нашёл пример с костью, но пропустил фрагмент с
  определением условной вероятности.
- Qwen вернула отказ на двух обычных вопросах. В Q07 все три размеченных
  фрагмента попали в контекст, но модель всё равно отказалась. В T01 она
  сослалась на текст, где отсутствовали запрошенные исторические сведения.
- Среди четырёх отказов на ловушках три вернула модель, один — приложение
  при пустой выдаче.
- В обоих прогонах судья ошибочно отклонил правильные ответы на Q03
  и Q10. Во втором прогоне он также пропустил явно указанное исключение
  нулевого вектора в Q02 и формулу первообразной в Q05. Диапазон 0–20%
  отражает нестабильность автоматической оценки на этом наборе.

Интеграционные тесты BM25 запускаются с `RUN_POSTGRES_TESTS=1` после миграций
командой `uv run -m pytest -m integration tests/integration/test_bm25_postgres.py`. Без переменной запускаются модульные тесты.
