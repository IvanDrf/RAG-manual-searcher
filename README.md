# RAG-manual-searcher

Сервис для поиска ответов в учебных пособиях и вузовских конспектах по математике.
Пользователь задаёт вопрос на русском языке, а сервис ищет подходящие фрагменты
материалов и передаёт их языковой модели как контекст для ответа — подход RAG
(Retrieval-Augmented Generation).

## Возможности

- Регистрация, вход, выход и обновление сессии.
- Вопросы по учебным материалам с ответами языковой модели.
- Создание чата при первом вопросе, получение списка чатов и истории, удаление чата.
- Просмотр названий книг, используемых для контекста.
- Управление ролями и блокировками пользователей администратором.

Сценарии использования, ограничения и направления развития описаны
в [продуктовой документации](spec/docs/product.md).

## Стек и структура

Backend: Python 3.12+, FastAPI, Pydantic, SQLAlchemy и Alembic.
Хранение данных: PostgreSQL с расширением pgvector и Redis.
Поиск выполняет собственная реализация BM25 с разреженными весами в pgvector.
Чат использует внешний LLM API с fallback моделей; модель бенчмарка задаётся в настройках.
Окружение: uv, Docker Compose, Prometheus и Grafana.

| Путь | Содержимое |
| --- | --- |
| `back/src/` | API, доменные модели, поиск и работа с хранилищами |
| `back/migrations/postgresql/alembic/` | Миграции схемы PostgreSQL |
| `back/scripts/` | Подготовка и импорт учебных материалов |
| `back/tests/` | Тесты backend |
| `data/` | PDF, текстовые материалы и промежуточные данные |
| `infrastructure/back/` | Docker Compose и настройки мониторинга |
| `spec/docs/` | Продуктовая документация и описание API |
| `spec/dev/` | Руководства для разработчиков |

## Подготовка окружения разработки

Нужны Python 3.12+, uv, Docker с Compose и make. Все команды выполняются
из корня репозитория. Создайте `.env` по образцу `.env.example`: в строках с `dev:` и `prod:`
оставьте только выбранное значение в формате `VARIABLE="value"`.
Для запуска на хосте выбирайте `dev`, для prod-контейнеров — `prod`.
Сохраните существующие настройки, если файл уже есть.

Заполните `.env`:

- `LLM_URL` — адрес API chat completions, `LLM_API_KEY` — ключ провайдера.
  Модели чата и fallback задаются в `back/src/api/chat.py`.
  `LLM_MODEL` задаёт модель автономного RAG и бенчмарка.
- `JWT_SECRET` — собственный секрет подписи токенов.
- `APP_PASSWORD_SALT` — корректная bcrypt-соль.
- `POSTGRES_*`, `REDIS_*` и `CLICKHOUSE_*` — параметры подключения.
  Для локального запуска используйте опубликованные порты соответствующих сервисов.

Подготовьте Python-окружение и русские ресурсы NLTK:

```bash
make back-setup
```

Поднимите PostgreSQL, Redis и ClickHouse, затем примените миграции схем:

```bash
make back-dev-up
make back-migrate-postgresql
make back-migrate-clickhouse
```

Импорт PDF в PostgreSQL сохраняет исходный текст страниц, нормализованный текст
и строит BM25-индекс. Это отдельная операция, изменяющая данные; выполняйте её
для подготовленного корпуса, а не при каждом запуске:

```bash
make back-data-migrate
```

По умолчанию книги берутся из `data/student_book_pdf`. Для другого каталога
задайте абсолютный путь через `BACK_BOOKS_DIR`; относительный путь считается от `back/`:

```bash
make back-data-migrate BACK_BOOKS_DIR=/path/to/books
```

Повторный импорт восстанавливает исходные тексты существующих страниц
при однозначном совпадении названия книги и нормализованного текста.
Проверьте отчёт импорта по пропущенным страницам.
Для перестроения индекса из уже сохранённых чанков:

```bash
make back-data-reindex
```

BM25 использует частоты термов, длины чанков, `k₁ = 1,2` и `b = 0,75`.
Нормализация запроса и страниц включает русскую токенизацию NLTK, удаление
стоп-слов и лемматизацию pymorphy3. Модель получает исходный текст с формулами
и условиями. PostgreSQL суммирует веса терминов запроса и отдаёт до трёх фрагментов.

Запуск backend:

```bash
make back-run
```

При стандартных `APP_HOST=localhost` и `APP_PORT=8080`:

- Swagger UI: <http://localhost:8080/docs>.
- Актуальная OpenAPI-схема: <http://localhost:8080/openapi.json>.
- Проверка доступности зависимостей: <http://localhost:8080/health>.

Для завершения процесса backend используйте Ctrl+C. Остановка сервисов:

```bash
make back-dev-down
```

Полный набор unit- и интеграционных тестов с отдельным тестовым окружением:

```bash
make run-test
```

Подробности — в [руководстве разработчика](spec/dev/manual.md)
и [руководстве по тестированию](spec/dev/testing.md).

## Запуск prod-окружения

Подготовьте корневой `.env` по образцу `.env.example`, выбрав значения `prod` и указав собственные
секреты и настройки LLM. Укажите пути корпуса через `BOOKS_SOURCE_DIR`
на хосте и `BOOKS_DIR` внутри контейнера, затем выполните:

```bash
make back-prod-up-build
```

По умолчанию контейнер backend включает расширение `vector`, применяет все миграции
PostgreSQL и ClickHouse, импортирует учебные материалы и строит BM25 до запуска API.
Команда показывает логи миграций, импорта и запуска backend, пока ждёт готовности
`/health`; ошибка подготовки останавливает запуск. Для дальнейшего просмотра
логов используйте `make back-prod-app-logs`. После готовности поток логов
автоматически завершается и терминал освобождается; контейнеры работают в фоне.
Ctrl+C во время просмотра логов прерывает только ожидание и просмотр.
Конфигурация передаётся при запуске, PDF подключаются только для чтения.
Для повторного запуска с готовыми томами в `.env` можно отключить отдельные этапы:
`RUN_POSTGRES_MIGRATIONS=false`, `RUN_CLICKHOUSE_MIGRATIONS=false`,
`RUN_DATA_MIGRATION=false`. Значение `0` также пропускает этап, `true`/`1`
включает его. Если флаг не задан, этап выполняется. После удаления томов
или появления новых миграций соответствующие этапы нужно включить снова.
Подробности перезапуска, томов и ограничений — в
[руководстве разработчика](spec/dev/manual.md#prod-окружение).

## Бенчмарк НИРС

Подробное описание score, метрик, формата отчёта и ограничений —
в [руководстве по бенчмарку](spec/dev/benchmark.md).

Набор содержит 30 фрагментов из математических книг, 10 обычных вопросов
и 5 ловушек. У каждого фрагмента указаны PDF и номер страницы, считая от
начала файла. Формулы приведены к текстовой записи. Разметка с эталонами
хранится в [data/benchmark/math.json](data/benchmark/math.json).

### Как запустить

Понадобятся Python 3.12+, uv, Docker Compose и доступ к LLM API,
совместимому с OpenAI Chat Completions. API должен поддерживать JSON-режим
`response_format: {"type": "json_object"}` для оценки ответов.
В корне репозитория подготовьте `.env` по образцу `.env.example` со значениями
`dev`, если своего файла ещё нет. Удалите обозначения `dev:`, `prod:` и `or`,
оставив одно выбранное значение для каждой переменной.
Задайте `LLM_URL`, `LLM_MODEL`, `LLM_API_KEY` и `LLM_REQUEST_TIMEOUT` для своего
провайдера. Модель используется и для генерации, и для оценки ответов.
Используемая модель:

```dotenv
LLM_MODEL="nvidia/nemotron-3-nano-omni-30b-a3b-reasoning:free"
```

`LLM_URL` должен указывать на chat completions API провайдера, у которого
доступна эта модель. Локальный сервер Ollama не требуется.

Отдельный `docker-compose.benchmark.yml` запускает только PostgreSQL с pgvector.
У него собственные сеть и том данных, отдельные от dev- и тестового окружений.
Порт задаётся через `POSTGRES_OUTPUT_PORT`; если dev-БД уже занимает его,
выберите свободный порт и задайте то же значение в `POSTGRES_PORT`.
Для запуска CLI на хосте используйте `POSTGRES_HOST=127.0.0.1`.

Полный запуск из корня репозитория:

```bash
make back-bench
```

По умолчанию одновременно обрабатываются четыре вопроса через `asyncio.gather`.
Генерация ответа и оценка для одного вопроса выполняются последовательно;
вопросы обрабатываются параллельно. Порядок вопросов в отчёте сохраняется.
Число параллельных вопросов можно изменить:

```bash
make back-bench BENCH_CONCURRENCY=8
```

Значение `BENCH_CONCURRENCY=1` возвращает последовательную обработку.
Выбирайте конкурентность с учётом лимитов LLM API.

Команда синхронизирует Python-окружение, поднимает PostgreSQL, включает расширение
vector через `back/scripts/data/init.sql` и применяет миграции,
запускает бенчмарк и выполняет `docker compose down`, в том числе при ошибке
или прерывании. Отчёт сохраняется в `data/benchmark/benchmark_YYYY-MM-DD_HH-MM-SS.json`;
том PostgreSQL сохраняется. Инициализация расширения выполняется и для уже
существующего тома. Перед первым прогоном подготовьте окружение и ресурсы NLTK:

```bash
make back-setup
```

Собственный набор и формат отчёта описаны в
[руководстве по бенчмарку](spec/dev/benchmark.md).

CLI создаёт временные таблицы на отдельном соединении с PostgreSQL. Для
бенчмарка достаточно миграций, разрешения создавать временные таблицы
и установленного pgvector с поддержкой `sparsevec`. Импорт книг, запуск
backend и Redis для бенчмарка не требуются.
Отчёт сохраняет Recall@3, MRR@3, Accuracy, Correct Rejection Rate, число
отказов, ответы и причины вердиктов. Recall@3 и MRR@3 считаются по десяти
обычным вопросам. На них же Accuracy измеряет полноту и корректность
ответа по смыслу. Correct Rejection Rate показывает долю точных отказов
на пяти ловушках. В роли судьи выступает та же модель Nemotron, поэтому
Accuracy отражает её автоматическую оценку. При ошибке генерации или
оценки CLI сохраняет неполный отчёт и завершает работу с кодом 1.

### Результаты контрольных прогонов

Два успешных прогона от 27 ноября 2026 на одном наборе: 30 фрагментов,
10 обычных вопросов и 5 ловушек. Генератор и судья —
`nvidia/nemotron-3-nano-omni-30b-a3b-reasoning:free`.
Время в таблице взято из имени файла отчёта (локальное время запуска).

| Прогон 27.11.2026 | Recall@3 | MRR@3 | Accuracy | Правильные отказы | Отказы на обычных вопросах | Ошибки |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| [23:14:08](data/benchmark/benchmark_2026-11-27_23-14-08.json) | 86,7% | 1.00 | 100,0% (10/10) | 100,0% (5/5) | 0 | 0 |
| [23:22:04](data/benchmark/benchmark_2026-11-27_23-22-04.json) | 86,7% | 1.00 | 100,0% (10/10) | 100,0% (5/5) | 0 | 0 |

Оба отчёта имеют `complete=true` и одинаковый `dataset_sha256`.
BM25 ставит релевантный фрагмент первым для каждого обычного вопроса,
но находит не все размеченные фрагменты в пределах тройки.
Модель-судья приняла все десять обычных ответов, все пять ловушек завершились
отказом. Accuracy отражает автоматическую оценку той же моделью,
а не независимую проверку человеком; результаты относятся к этому небольшому набору.

Интеграционные тесты BM25 входят в `make run-test` и используют тестовую БД
из `infrastructure/back/docker-compose.test.yml`. Дополнительные переменные
окружения и ручное применение миграций для этих тестов не нужны.
