# Руководство разработчика

Все команды выполняются из корня репозитория. Их реализация находится
в [Makefile](../../Makefile); переход в `back/` выполняется внутри нужных целей.

Для локальной разработки нужны Python 3.12+, `uv`, `make`, Docker и Compose v2.
Команды окружений используют `docker compose`; prod-запуск использует
проверку состояния backend через `docker compose ps` для ожидания готовности.

Перед запуском приложения создайте корневой `.env` по образцу
[.env.example](../../.env.example): в строках `VARIABLE=dev:"value" or prod:"value"`
выберите значение для нужного режима и оставьте `VARIABLE="value"`.
Для локального backend выбирайте `dev`, для prod-контейнера — `prod`.
Задайте свои параметры подключения, секреты и настройки LLM. Команды подготовки не создают `.env` автоматически.

## Подготовка и запуск backend

- `make back-setup` — синхронизирует Python-зависимости из `back/uv.lock`, включая dev-группу, и загружает ресурсы NLTK `stopwords`, `punkt`, `punkt_tab` для текущего пользователя. Базы данных и приложение не запускает.

- `make back-migrate-postgresql` — применяет все неприменённые миграции схемы PostgreSQL до последней ревизии через `migrations/postgresql/alembic.ini`. Использует подключение из конфигурации приложения; БД должна быть доступна, а расширение `vector` — включено.

- `make back-migrate-clickhouse` — применяет миграции схемы ClickHouse до последней ревизии через `migrations/clickhouse/alembic.ini`. ClickHouse должен быть доступен по настроенному адресу.

- `make back-run` — запускает FastAPI backend на хосте через модуль `src.app.main`. Адрес и порт берутся из настроек приложения. Команда работает в текущем терминале; Ctrl+C завершает процесс. Контейнеры зависимостей автоматически не поднимаются.

Миграции схемы меняют таблицы и структуру хранилищ. Импорт учебных материалов
выполняется отдельно командами следующего раздела.

## Учебные материалы и поисковый индекс

- `make back-data-migrate` — выполняет модуль `scripts.data.data_migration` из `back/`: обрабатывает PDF, импортирует книги и фрагменты в PostgreSQL и строит BM25-индекс. По умолчанию читает `data/student_book_pdf`. Требует доступную БД с применёнными миграциями и подготовленные ресурсы NLTK.

- `make back-data-migrate BACK_BOOKS_DIR=/path/to/books` — выполняет тот же импорт из указанного каталога. Абсолютный путь используется напрямую; относительный считается от `back/`. Аргумент с пробелами заключайте в кавычки, например `BACK_BOOKS_DIR="/path/to/my books"`.

- `make back-data-reindex` — перестраивает BM25-индекс из уже сохранённых чанков с заполненным исходным текстом `source_text`. PDF не читает и отсутствующие исходники не восстанавливает.

Импорт и перестроение индекса изменяют данные. Повторный импорт восстанавливает
исходники старых чанков только при однозначном совпадении книги и нормализованного
текста; проверьте сообщения о пропущенных страницах. Нулевое число проиндексированных
фрагментов может означать отсутствие чанков с `source_text`.

## Dev-окружение

Команды используют
[docker-compose.dev.yml](../../infrastructure/back/docker-compose.dev.yml).
В текущем файле определены PostgreSQL с pgvector, Redis и ClickHouse.
Сам backend запускается отдельно через `make back-run`.

- `make back-dev-up` — создаёт и запускает dev-контейнеры в фоновом режиме, используя корневой `.env`. Не применяет Alembic-миграции и не импортирует книги. Завершение команды не означает, что все сервисы уже готовы принимать запросы.

- `make back-dev-up-build` — выполняет тот же запуск с флагом `--build`, пересобирая сервисы, у которых задан `build`. В текущем dev-файле используются готовые образы, поэтому локальных сервисов для сборки нет.

- `make back-dev-down` — останавливает и удаляет контейнеры и сеть dev-окружения, сохраняя именованные тома с данными. Процесс backend, запущенный на хосте, не останавливает.

- `make back-dev-down-volumes` — выполняет остановку dev-окружения с `down -v`: дополнительно удаляет его именованные и подключённые анонимные тома. Это удаляет сохранённые в этих томах данные PostgreSQL, Redis и ClickHouse.

## Prod-окружение

Команды используют
[docker-compose.prod.yml](../../infrastructure/back/docker-compose.prod.yml).
В нём определены backend, PostgreSQL, Redis, ClickHouse, Prometheus и Grafana.
Для backend Compose читает корневой `.env` через `env_file` и передаёт его
переменные процессу без дублирования списка `environment`. Файл не входит в образ.
Параметры PostgreSQL, ClickHouse и Grafana подставляются через `${ENV_VALUE}`. Для prod используйте шаблон
[.env.example](../../.env.example), выбирая значения `prod`. Укажите в `.env` `APP_HOST=0.0.0.0`,
`POSTGRES_HOST=database`, `REDIS_HOST=redis_db`, `CLICKHOUSE_HOST=clickhouse`;
порты подключения внутри сети — `5432`, `6379` и HTTP-порт ClickHouse `8123`.
`APP_PORT` задаёт порт backend внутри контейнера, `APP_OUTPUT_PORT` — на хосте.
Compose не заменяет эти значения автоматически.

`BOOKS_SOURCE_DIR` задаёт каталог PDF на хосте, относительно Compose-файла
(по шаблону `../../data/student_book_pdf`) или абсолютным путём.
`BOOKS_DIR` задаёт точку подключения внутри контейнера
(по шаблону `/app/data/student_book_pdf`). Каталог подключается только для чтения,
должен существовать и содержать материалы с извлекаемым текстом.
Для другого корпуса измените `BOOKS_SOURCE_DIR` в `.env`.
NLTK-ресурсы загружаются при сборке образа, поэтому во время старта их загрузка
из интернета не требуется.

После готовности PostgreSQL, Redis и ClickHouse entrypoint по умолчанию выполняет по порядку:

1. Включение PostgreSQL-расширения `vector`, в том числе на существующем томе.
2. Все миграции PostgreSQL.
3. Все миграции ClickHouse.
4. Импорт PDF и построение BM25-индекса.
5. Запуск FastAPI.

Ошибка любого шага останавливает запуск. Отсутствие PDF и нулевой индекс после
импорта считаются ошибками, если импорт включён. По умолчанию он выполняется при каждом запуске контейнера:
существующие книги сопоставляются текущим скриптом импорта, затем индекс перестраивается.
Это может занимать заметное время на большом корпусе; команды prod-запуска ждут
проверки `/health` до 1800 секунд и одновременно выводят логи backend: миграции,
импорт PDF, построение BM25 и запуск сервера. После статуса `healthy` просмотр логов автоматически завершается,
команда возвращает приглашение терминала, а контейнеры продолжают работать.
Во время просмотра Ctrl+C завершает ожидание и вывод логов без вызова
`stop` или `down`. После запуска в фоне готовность проверяется только чтением
состояния контейнера через `docker compose ps`, повторный `up` не вызывается. При ошибке ожидания возвращается ненулевой код;
поток логов завершается, но контейнеры автоматически не удаляются. Проверка не вызывает внешний LLM API:
доступность провайдера и корректность его модели/ключа задаются отдельно.
Параллельное развёртывание нескольких реплик с одновременными миграциями
этим entrypoint не координируется.

### Флаги подготовки контейнера

| Переменная в `.env` | Управляемый этап |
| --- | --- |
| `RUN_POSTGRES_MIGRATIONS` | Включение расширения `vector` и миграции PostgreSQL |
| `RUN_CLICKHOUSE_MIGRATIONS` | Миграции ClickHouse |
| `RUN_DATA_MIGRATION` | Импорт PDF и перестроение BM25-индекса |

Для каждой переменной `true` или `1` включает этап, `false` или `0` пропускает.
Регистр `true`/`false` может быть нижним, верхним или с заглавной первой буквой.
Если переменная отсутствует, этап включён. Пустые и неподдерживаемые значения
останавливают entrypoint до подключения к БД. В логах видны выполненные
и пропущенные этапы. Ошибка включённого этапа по-прежнему блокирует запуск API.

При первом запуске оставьте все флаги включёнными. Для быстрого запуска
с уже подготовленными томами и актуальной схемой можно задать:

```dotenv
RUN_POSTGRES_MIGRATIONS=false
RUN_CLICKHOUSE_MIGRATIONS=0
RUN_DATA_MIGRATION=false
```

Тогда entrypoint сразу запустит приложение. PostgreSQL, Redis и ClickHouse
по-прежнему должны пройти healthcheck; сохранённые данные и индекс используются
как есть. Пропуск импорта сам по себе не проверяет, что корпус уже заполнен.
После удаления томов включите все этапы снова; при новых миграциях кода включите
флаг соответствующего хранилища, а при обновлении PDF — импорт данных.

Флаги читает shell entrypoint из окружения процесса. Compose передаёт их через
`env_file` без дополнительных записей в `environment`. После изменения `.env`
используйте `make back-prod-up`, чтобы пересоздать контейнер с новыми значениями;
обычный `docker restart` не перечитывает `env_file`. После изменения самого
entrypoint требуется `make back-prod-up-build`.
Прямые команды `make back-migrate-postgresql`, `make back-migrate-clickhouse`,
`make back-data-migrate`, `make back-data-reindex` и бенчмарк эти флаги не учитывают.

- `make back-prod-up` — создаёт и запускает prod-окружение в фоне, выводит логи backend и ждёт готовности сервисов. Entrypoint backend выполняет включённые env-флагами миграции и импорт до запуска API. Использует существующий образ; после изменения кода сначала пересоберите его.

- `make back-prod-up-build` — собирает backend и NLTK-ресурсы из Dockerfile, запускает prod-окружение с флагом `--build` и показывает логи backend до успешной проверки `/health` после включённых миграций и импорта.

- `make back-prod-down` — останавливает и удаляет prod-контейнеры и сеть, сохраняя именованные тома.

- `make back-prod-down-volumes` — останавливает prod-окружение и удаляет его тома через `down -v`, включая данные PostgreSQL, Redis, ClickHouse и сохранённые настройки Grafana.

- `make back-prod-app-logs` — показывает последние 100 строк логов backend и продолжает выводить новые строки в реальном времени. Ctrl+C завершает просмотр, не останавливая контейнер.

## Тесты

- `make run-test` — синхронизирует Python-окружение с dev-зависимостями, запускает изолированные PostgreSQL, Redis и ClickHouse через `docker-compose.test.yml`, ждёт их готовности и выполняет все unit- и интеграционные тесты. После завершения, ошибки или обрабатываемого сигнала останавливает и удаляет тестовое окружение. При ошибке тестов, запуска сервисов или очистки возвращает ненулевой код.

Тесты не обращаются к платному LLM API. PostgreSQL и ClickHouse тестового
окружения хранят данные в tmpfs; после удаления контейнеров они не сохраняются.
Подробности и варианты выборочного запуска — в [руководстве по тестированию](testing.md).

## Бенчмарк

- `make back-bench` — синхронизирует Python-окружение, поднимает PostgreSQL с pgvector через `docker-compose.benchmark.yml`, ждёт готовности, выполняет `init.sql`, применяет миграции PostgreSQL и запускает бенчмарк. Записывает отчёт в `data/benchmark/benchmark_YYYY-MM-DD_HH-MM-SS.json`. После завершения, ошибки или обрабатываемого сигнала выполняет `docker compose down`, сохраняя том БД.

- `make back-bench BENCH_CONCURRENCY=8` — выполняет тот же бенчмарк с восемью параллельно обрабатываемыми вопросами. По умолчанию Makefile передаёт `4`; значение `1` включает последовательную обработку.

Перед первым прогоном выполните `make back-setup` и настройте LLM API.
Бенчмарк действительно отправляет запросы провайдеру, использует одну модель
для генерации и оценки и расходует его квоты. Импорт PDF для него не требуется.
Описание `score`, метрик, набора и отчёта — в [руководстве по бенчмарку](benchmark.md).
