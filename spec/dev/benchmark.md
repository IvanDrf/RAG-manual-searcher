# Бенчмарк поиска и ответов LLM

Бенчмарк проверяет две части RAG отдельно: поиск фрагментов через BM25 и ответы
языковой модели по найденному контексту. Основная реализация —
[benchmark_rag.py](../../back/scripts/benchmark_rag.py), контрольный набор —
[math.json](../../data/benchmark/math.json).

Это проверка качества на фиксированном наборе, а не нагрузочный тест HTTP API.
Она не проходит через авторизацию, обработчик чата, историю и аналитику ClickHouse.
Модель берётся из `LLM_MODEL`; fallback-модели чата здесь не используются.

## Что происходит при запуске

1. CLI читает JSON, проверяет разметку и вычисляет SHA-256 исходных байтов файла.
2. На отдельном соединении PostgreSQL создаются временные `books`, `chunks`,
   `bm25_terms` и `bm25_blocks` по структуре существующих таблиц.
3. Фрагменты набора нормализуются и загружаются во временные таблицы.
   По ним строится отдельный BM25-индекс.
4. Для каждого вопроса выполняется поиск до трёх фрагментов. Этот этап идёт
   последовательно, в одной сессии БД, до запуска запросов к LLM.
5. Вопросы параллельно проходят генерацию ответа и, для обычных вопросов,
   оценку моделью-судьёй. Для одного вопроса генерация предшествует оценке.
6. CLI записывает JSON-отчёт и выводит агрегированные метрики в терминал.

Временные таблицы удаляются при завершении транзакции. Рабочий корпус не участвует
в ранжировании бенчмарка. Импорт PDF и `--reindex` перед прогоном не нужны.
Миграции и включение расширения `vector` изменяют схему выделенной benchmark-БД;
сами фрагменты контрольного набора в постоянных таблицах не сохраняются.

## Подготовка и запуск

Нужны Python 3.12+, `uv`, Docker Compose v2, `make` и LLM API, совместимый
с OpenAI Chat Completions. Backend, Redis и ClickHouse запускать не требуется.
PostgreSQL использует образ `pgvector/pgvector:pg17-trixie` с типами `vector` и `sparsevec`.

Подготовьте корневой `.env` по образцу [.env.example](../../.env.example),
выбирая значения `dev`: CLI бенчмарка запускается на хосте.
Для строки `VARIABLE=dev:"value" or prod:"value"` оставьте только
`VARIABLE="value"` нужного режима. Не перезаписывайте существующую конфигурацию.

| Переменная | Назначение |
| --- | --- |
| `LLM_URL` | Полный URL endpoint chat completions |
| `LLM_MODEL` | Идентификатор модели именно у выбранного провайдера |
| `LLM_API_KEY` | Ключ API, отправляемый в заголовке Bearer |
| `LLM_REQUEST_TIMEOUT` | Таймаут HTTP-клиента в секундах; например, `120` |
| `POSTGRES_HOST` | Для запуска CLI с хоста — `127.0.0.1` |
| `POSTGRES_PORT` | Порт подключения CLI к benchmark-БД |
| `POSTGRES_OUTPUT_PORT` | Публикуемый Docker порт; должен совпадать с `POSTGRES_PORT` |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | Учётные данные и имя benchmark-БД |

Бенчмарк импортирует общую конфигурацию приложения: остальные обязательные поля,
например `APP_EMBEDDING_SIZE`, `APP_PASSWORD_SALT`, `JWT_SECRET`, также должны
проходить валидацию. Наличие этих настроек не означает запуск авторизации.

Для текущих контрольных прогонов используются модель Nemotron и внешний LLM API:

```dotenv
LLM_MODEL="nvidia/nemotron-3-nano-omni-30b-a3b-reasoning:free"
LLM_REQUEST_TIMEOUT=120
```

Задайте `LLM_URL` и `LLM_API_KEY` своего провайдера, поддерживающего эту модель.
Локальный Ollama не требуется. Этот идентификатор задан также в `.env.example`
и как значение модели по умолчанию в конфигурации backend.

Один раз подготовьте Python-окружение и ресурсы нормализации из корня репозитория:

```bash
uv sync --project back --locked --no-install-project
cd back
uv run --no-sync python -m nltk.downloader stopwords punkt punkt_tab
cd ..
```

### Полный запуск через Makefile

Из корня репозитория:

```bash
make back-bench
```

Команда синхронизирует окружение, поднимает только PostgreSQL через
[docker-compose.benchmark.yml](../../infrastructure/back/docker-compose.benchmark.yml),
ждёт готовности, выполняет [init.sql](../../back/scripts/data/init.sql), применяет
PostgreSQL-миграции и запускает CLI. `init.sql` включает расширение `vector`
и выполняется также для уже созданного тома.

Отчёт сохраняется в `data/benchmark/benchmark_YYYY-MM-DD_HH-MM-SS.json`.
Дата и время в имени берутся из локального времени системы. Два запуска в одну
секунду могут выбрать одинаковый путь; существующий отчёт по этому пути перезаписывается.

При завершении, ошибке или обрабатываемом сигнале выполняется `docker compose down`.
Том PostgreSQL сохраняется. Принудительное завершение через SIGKILL не позволяет
shell выполнить очистку. При необходимости остановите окружение вручную:

```bash
docker compose --env-file .env -f infrastructure/back/docker-compose.benchmark.yml down
```

У benchmark-окружения отдельные сеть и том. Если порт занят dev-БД, выберите другой
свободный порт в обеих переменных `POSTGRES_PORT` и `POSTGRES_OUTPUT_PORT`.

### Конкурентность

```bash
make back-bench BENCH_CONCURRENCY=8
```

`BENCH_CONCURRENCY` ограничивает число одновременно обрабатываемых вопросов.
Используются `asyncio.gather`, семафор и общий `httpx.AsyncClient`.
Внутри одного вопроса одновременно выполняется не больше одного LLM-запроса;
оценка ждёт генерации. Результаты в JSON сохраняют исходный порядок вопросов,
даже если ответы пришли в другом порядке.

Значение `1` задаёт последовательную обработку. При неожиданном исключении
оставшиеся задачи отменяются и дожидаются завершения до закрытия HTTP-клиента.
Ожидаемые ошибки отдельного вопроса сохраняются в отчёт, остальные вопросы продолжаются.

В текущем коде значения по умолчанию расходятся: Makefile передаёт `4`, CLI без
`--concurrency` выбирает `7`, а прямой вызов `run_benchmark` без аргумента — `8`.
Текст CLI-help пока указывает `4`. Для сравнимых прогонов задавайте значение явно.
Конкурентность не записывается в JSON-отчёт, поэтому сохраняйте её отдельно.

Большая конкурентность может уменьшить время ожидания, если провайдер допускает
параллельную обработку. Она не ограничивает число запросов в минуту, не гарантирует
линейного ускорения и может приводить к HTTP 429.

## Контрольный набор и разметка

В JSON два массива: `fragments` и `questions`.

| Объект | Поля |
| --- | --- |
| Фрагмент | `id` — уникальный ID; `book` — источник; `page` — номер страницы PDF от начала файла; `text` — исходный текст |
| Вопрос | `id` — уникальный ID; `text` — вопрос; `reference` — эталон ответа; `relevant_ids` — ID релевантных фрагментов |

Текущая проверка требует ровно 30 уникальных фрагментов и 15 уникальных вопросов:
10 обычных и 5 ловушек. Обычный вопрос имеет не менее трёх различных релевантных ID,
все они должны существовать в `fragments`. Ловушка имеет пустой `relevant_ids`.
Поэтому `--dataset` не позволяет произвольно изменить размер контрольного набора.

Тексты набора уже подготовлены. PDF при прогоне не открываются, формулы читаются
из `text`. Поля `book` и `page` служат сведениями об источнике, а не командой загрузки PDF.

## Что означает score

`questions[].hits[].score` — численная оценка соответствия одного фрагмента
запросу по BM25. Чем она выше, тем раньше фрагмент располагается в выдаче
**для этого запроса на этом корпусе**.

Это не процент, не вероятность правильного ответа, не оценка моделью-судьёй
и не косинусное сходство. Значение может быть больше единицы. Например,
`score = 8` не означает ни 80%, ни вдвое более качественный ответ, чем при `score = 4`.

### Нормализация и формула

Вопрос и фрагменты проходят `casefold`, русскую токенизацию NLTK, удаление
стоп-слов и неалфавитных токенов, затем лемматизацию через pymorphy3.
В BM25 попадает нормализованный текст, а в промпт LLM — исходные фрагменты.
Числа и многие математические обозначения не проходят фильтр `isalpha`,
поэтому совпадение формул само по себе не гарантирует высокий поисковый балл.

В реализации [bm25.py](../../back/src/infrastructure/rag/bm25.py):

```text
IDF(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))

weight(t, d) = IDF(t) × tf(t, d) × (k1 + 1)
               / (tf(t, d) + k1 × (1 - b + b × length(d) / avg_length))

score(q, d) = сумма weight(t, d) по уникальным термам запроса q
```

| Обозначение | Смысл |
| --- | --- |
| `N` | Число индексируемых фрагментов |
| `df(t)` | Число фрагментов, содержащих терм `t` |
| `tf(t, d)` | Число вхождений терма в конкретный фрагмент |
| `length(d)` | Число токенов нормализованного фрагмента |
| `avg_length` | Средняя длина индексируемых фрагментов |
| `k1 = 1.2` | Управляет насыщением вклада повторяющихся слов |
| `b = 0.75` | Управляет нормализацией по длине фрагмента |

Редкие в корпусе слова дают больший вклад. Повторение слова внутри фрагмента
увеличивает вклад с насыщением; длина учитывается относительно средней.
Повторение одного слова в запросе не увеличивает его вес: SQL выбирает термы
через `WHERE term = ANY(:terms)`.

Веса хранятся в блоках `sparsevec` размерности 1000. PostgreSQL вычисляет
скалярные произведения с вектором запроса и суммирует их по блокам.
Разбиение на блоки не является дополнительной метрикой.

Поиск возвращает до трёх фрагментов с `score > 0` и заполненным `source_text`.
При равных баллах порядок задаётся `chunk_id`; в бенчмарке эти UUID назначаются
по отсортированным ID фрагментов. Порог качества сверх условия `score > 0` не задан.
Положительный score означает лексическое совпадение, а не достаточность контекста.

Сравнивать абсолютные score разных вопросов или корпусов как единую шкалу
нельзя: они зависят от слов запроса, частот и длин фрагментов.
Добавление документов меняет статистику IDF и среднюю длину.

## Метрики

Все доли в JSON записаны от `0` до `1`: `0.8` означает `80%`.
Счётчики записаны целыми числами. `null` означает, что оценка не получена,
а не нулевое качество. Единого итогового балла бенчмарк не вычисляет.

### Recall@3 — полнота поиска

Для обычного вопроса:

```text
recall_at_3 = число релевантных фрагментов среди первых трёх
              / общее число размеченных релевантных фрагментов
```

Если размечены `D01`, `D02`, `D03`, а найдены `D01`, `D08`, `D03`, значение равно
`2/3`. Пустая выдача даёт `0`. В `metrics.recall_at_3` записано среднее
по десяти обычным вопросам; ловушки исключены.

Если у вопроса размечено больше трёх релевантных фрагментов, Recall@3 не сможет
достичь единицы даже при трёх релевантных результатах. Это следствие знаменателя.

### MRR@3 — позиция первого релевантного фрагмента

Для вопроса поле называется `reciprocal_rank_at_3`:

| Первый релевантный результат | Значение |
| --- | --- |
| На позиции 1 | `1` |
| На позиции 2 | `1/2` |
| На позиции 3 | `1/3` |
| В первых трёх отсутствует | `0` |

`metrics.mrr_at_3` — среднее этих значений по десяти обычным вопросам.
Например, `MRR@3 = 1` и `Recall@3 = 0.8667` совместимы: первый результат всегда
релевантен, но часть других нужных фрагментов не попала в тройку.

Обе поисковые метрики вычисляются до вызовов LLM и могут быть корректно
рассчитаны даже при отказе провайдера на всех запросах генерации.

### Accuracy — оценка ответов моделью

```text
accuracy = число обычных вопросов с verdict.correct = true / 10
```

Судья получает вопрос, эталон и ответ. Он сравнивает смысл, условия и
математическую корректность, допускает перефразировку и должен отклонять
частичные ответы. Номера цитируемых фрагментов предписано игнорировать.
Исходные найденные тексты в запрос судьи отдельно не передаются.

Судья возвращает `{"correct": true, "reason": "..."}` или аналогичный объект
с `false`. Валидатор требует настоящий boolean, непустое обоснование после
удаления краевых пробелов и отсутствие посторонних полей.

Если на обычный вопрос вернулся точный отказ, CLI сам записывает `correct=false`
без запроса судье. Если хотя бы по одному обычному вопросу вердикта нет,
агрегированная `accuracy` равна `null`; отсутствующий вердикт не заменяется нулём.

Генератор и судья используют одну модель из `LLM_MODEL`. Поэтому Accuracy —
автоматическая оценка с возможными ошибками, а не подтверждённая человеком точность.
Высокие Recall/MRR не гарантируют правильный ответ LLM.

### Correct Rejection Rate — отказы на ловушках

```text
correct_rejection_rate = число ловушек с точным отказом / 5
```

Текущая фраза отказа из `rag.py`:

```text
Нет ответа в прикреплённых данных
```

CLI сравнивает ответ с этой строкой после удаления краевых пробелов HTTP-клиентом.
Лишняя точка, кавычки или объяснение мешают точному совпадению. Ответ
«Недостаточно данных в конспекте» в текущем бенчмарке не считается этим отказом.

При пустой выдаче CLI возвращает отказ без LLM-запроса (`empty_retrieval`).
При непустой выдаче точный отказ модели помечается `model`.
Оба случая учитываются в Correct Rejection Rate. Судья для ловушек не вызывается.
Если хотя бы на одной ловушке произошла ошибка, метрика равна `null`.

### Счётчики

| Поле в `metrics` | Смысл |
| --- | --- |
| `ordinary_refusals` | Сколько из десяти обычных вопросов получили точный отказ |
| `trap_refusals` | Сколько из пяти ловушек получили точный отказ |
| `failed_questions` | Сколько вопросов имеют непустое поле `error`, независимо от стадии |

Отказ — результат работы сценария, а ошибка — сбой его выполнения.
Например, HTTP 400 не увеличивает счётчик отказов. При отсутствии ошибок
`correct_rejection_rate = trap_refusals / 5`.

## Формат JSON-отчёта

| Поле верхнего уровня | Содержание |
| --- | --- |
| `started_at` | Время начала `run_benchmark` в UTC, включая поиск |
| `dataset_sha256` | SHA-256 байтов входного JSON; меняется даже при изменении форматирования |
| `top_k` | Максимальный размер выдачи, сейчас `3` |
| `model` | Модель генерации |
| `judge_model` | Модель оценки, сейчас совпадает с `model` |
| `complete` | `true`, если `failed_questions == 0`; не означает правильность всех ответов |
| `metrics` | Агрегированные метрики и счётчики |
| `questions` | Результаты в исходном порядке вопросов набора |

| Поле элемента `questions` | Содержание |
| --- | --- |
| `question` | Исходные `id`, `text`, `reference`, `relevant_ids` |
| `hits` | Найденные фрагменты в порядке ранжирования: `id`, `book`, `page`, `score` |
| `answer` | Ответ модели или автоматический отказ; при ошибке генерации обычно `null` |
| `refusal` | `null`, `empty_retrieval` или `model` |
| `verdict` | `correct` и `reason`; для ловушек и при отсутствии оценки — `null` |
| `error` | `null` или строка со стадией `generation:` / `judge:` и описанием ошибки |
| `recall_at_3` | Полнота поиска для обычного вопроса; для ловушки — `null` |
| `reciprocal_rank_at_3` | Обратный ранг для обычного вопроса; для ловушки — `null` |

При ошибке судьи уже сгенерированный `answer` остаётся в отчёте.
Полные исходные тексты `hits` не дублируются в отчёте: их можно найти по `id`
в том же наборе данных. Метки `[CHUNK 1]` в ответе обозначают позицию в выдаче
этого вопроса, а не постоянный ID `D01`.

Длительность, токены, стоимость, число HTTP-попыток, URL провайдера и настройки
конкурентности текущий JSON не сохраняет. `started_at` не является измерением
задержки отдельного запроса.

## Ошибки и повторные запросы

Клиент ожидает HTTP 200 и непустой текст в `choices[0].message.content`.
В запросах бенчмарка задана `temperature=0`, в запросах судьи дополнительно
`response_format={"type":"json_object"}`. Провайдер должен поддерживать этот формат.

Декоратор с названием `circuit_breaker` фактически выполняет до трёх попыток
при `ExternalError`: например, при неуспешном HTTP-статусе или некорректном JSON
ответа API. Он не имеет общего состояния, отключающего запросы после серии сбоев.
Паузы увеличиваются с 0.5 секунды; текущий код делает паузу и после последней
неуспешной попытки. Сетевые исключения HTTPX этим декоратором не повторяются.
Ошибка структуры вердикта после успешного HTTP-ответа также не вызывает повтор
самого запроса судьи.

В штатном прогоне возможно до 15 запросов генерации и до 10 запросов оценки,
без учёта повторов. Пустая выдача и отказы уменьшают это число. Параллельный
запуск меняет время выполнения, но не устраняет плату за запросы провайдера.

Ожидаемые ошибки генерации и оценки сохраняются по вопросам. CLI пишет неполный
отчёт и завершает работу с кодом `1`, если есть `failed_questions`.
При успешном прогоне код `0`, даже если все ответы получили `correct=false`.
`make` также завершится ненулевым кодом при ошибке CLI или очистки окружения.

Отчёт не гарантирован при ошибке конфигурации, чтения/валидации набора, подключения
к БД, поиска, неожиданном исключении или прерывании до записи файла.
`--output` не сохраняет промежуточный прогресс после каждого вопроса.

| Симптом | Что проверить |
| --- | --- |
| `type "vector" does not exist` | Выполнен ли `init.sql` в нужной БД до миграций |
| `relation "bm25_terms" does not exist` | Применены ли PostgreSQL-миграции к БД, указанной в настройках |
| Ошибка поиска ресурсов NLTK | Установлены ли `stopwords`, `punkt`, `punkt_tab` для текущего пользователя |
| HTTP 400 | Имя модели и поддержка отправляемых параметров; для точной причины нужен ответ провайдера |
| HTTP 401/403 | Действительность ключа и права доступа к модели |
| HTTP 429 | Лимиты провайдера и конкурентность; попробуйте `BENCH_CONCURRENCY=1` |
| Поисковые метрики есть, Accuracy — `null` | Посмотрите `questions[].error`: поиск мог завершиться успешно, а LLM или судья — нет |

Не публикуйте `.env`, API-ключи и заголовки авторизации вместе с отчётом.

## Как сравнивать прогоны

Для осмысленного сравнения сохраняйте одинаковый набор (`dataset_sha256`),
версию кода, параметры BM25, `top_k`, провайдера, модель и конкурентность.
Меняйте один фактор за прогон и сохраняйте результаты в разные файлы.
`temperature=0` не гарантирует побитовую воспроизводимость внешнего API.

Сначала проверьте `complete` и `failed_questions`, затем Recall/MRR, после них
Accuracy и отказы. Просматривайте конкретные `hits`, `answer` и `verdict.reason`:
средние значения скрывают пропущенные условия и ошибки судьи.

Набор мал: один обычный вопрос меняет Accuracy на 10 процентных пунктов,
одна ловушка — Correct Rejection Rate на 20. Разметка может быть неполной,
а судья может ошибаться и при принятии, и при отклонении ответа.
